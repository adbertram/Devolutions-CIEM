Core Concepts

The module is built around six key concepts that flow from configuration through to results display.

Concept

Provider

A configured cloud platform (Azure or AWS) with its authentication method, API endpoints, and optional subscription/account filters.

Concept

Service

A logical grouping of cloud resources (e.g. Entra, IAM, KeyVault, Storage). Each service has an initialization script that pre-fetches all relevant API data.

Concept

Check

A single security rule defined in a shared metadata file. Includes title, description, severity, risk, remediation guidance, and required permissions.

Concept

Scan Result

The outcome of running one check against one resource. Carries a status — PASS FAIL MANUAL SKIPPED — plus details and the affected resource.

Concept

Scan Run

A top-level container grouping all results from a single scan execution. Tracks status (Running Completed Failed), timing, and aggregate counts.

Concept

Service Cache

The pre-fetched API data for a service, wrapped with success/failure status and timing. Checks read from this cache — they never call cloud APIs directly.

2

How They Fit Together

A Provider authenticates to the cloud. Services fetch data from that cloud. Checks assert conditions against the fetched data. Results are collected into a Scan Run.

Provider ──authenticates──▸ Service ──pre-fetches──▸ Service Cache │ Check ───────────reads from──────────────────────┘ │ │ emits 0–N ▾ Scan Result ──collected into──▸ Scan Run
3

Authentication

Each provider carries an authentication context. Azure supports five methods; AWS supports two. The model is polymorphic — every method shares a common base (provider, enabled, method) while adding its own fields (tenant ID, client ID, region, etc.).

Azure — 5 Methods

Azure Authentication

Service Principal (Secret) — Tenant ID + Client ID + Client Secret
Service Principal (Certificate) — Tenant ID + Client ID + Cert Thumbprint
Managed Identity — Zero-config for Azure Web App hosting
Device Code — Interactive code-based login
Interactive Browser — Browser-based sign-in
AWS — 2 Methods

AWS Authentication

Current Profile — Uses existing AWS CLI config (~/.aws/credentials)
Access Key — Access Key ID + Secret Access Key + Region
AWS support is staged for future implementation.

The "Gather Then Assert" Architecture

The scan engine uses a two-phase pattern that separates data collection from evaluation. This is the most important architectural decision in the module.

Without this pattern

Each check calls cloud APIs independently. 15 Entra checks = 15 duplicate calls to the same endpoints. Slow, rate-limited, wasteful.

With this pattern

Each service calls its APIs once, caches the results in memory. All checks read from that shared cache. Fast, efficient, no duplicate calls.

Phase 1 — Services Gather

Pre-fetch all cloud data into service caches

Each of the 20 Azure service scripts (Entra, IAM, KeyVault, Storage, Defender, Monitor, Network, App, Vm, etc.) calls the relevant cloud APIs and returns a data structure. The orchestrator wraps each result with success/failure status and timing metadata.

Tenant-Scoped
Entra — Users, MFA status, directory roles + members, security defaults, authorization policy, conditional access policies, named locations
Subscription-Scoped
IAM — Role definitions, custom roles, role assignments
Storage — Storage accounts, blob settings
(Data keyed by subscription ID)
Multi-Plane
KeyVault — ARM management plane (vault list, diagnostics) + data plane (keys, secrets). Gracefully handles 403 on data plane access.
Phase 2 — Checks Assert

Evaluate cached data against security rules

Every check follows the same contract: it receives check metadata and one or more service caches, then returns zero or more scan results. No check ever makes an API call — it's pure in-memory evaluation.

Simple assertions
"Is security defaults enabled?" — reads one property, returns one PASS or FAIL.
"Are there fewer than 5 Global Admins?" — counts members, compares to threshold.
Per-resource assertions
"Do all privileged users have MFA?" — cross-references role members with MFA status, emits one FAIL per user without MFA. A single check can produce N results.

Dependency & Auto-Skip

Checks declare which services they depend on. If a service failed to initialize (e.g. missing API permissions), all checks that depend on it are automatically skipped with an explanation — no check code runs at all.

Prowler Sync — Growing the Check Library

Checks are not written from scratch. They originate from Prowler, an open-source Python cloud security tool. A built-in sync pipeline imports new checks from the Prowler GitHub repository and converts them to CIEM-compatible PowerShell.

Auto-populated from Prowler

Check ID, title, description, risk assessment, severity level, remediation URL, related documentation, service name, and inferred permissions.

Requires manual work

The assertion logic (reading service cache data, evaluating conditions, emitting results). May also need a new service script if the check targets a new cloud service.

Efficient incremental sync

The full Prowler repository tree is fetched in a single cached GitHub API call. When no new checks exist, the operation completes with just that one call — no git clone needed. For bulk imports, sparse checkout downloads only the new directories regardless of count.

Data Persistence

All persistent state is stored in the PSU cache (key-value store with optional persistence to disk). Sensitive credentials are stored separately in PSU's encrypted secrets store.

PSU Cache

Configuration & scan data

Config — Global scan settings and active provider.
Providers — Provider configs with auth context and endpoints.
Scan Runs — Per-run metadata (status, timing, counts). One key per run.
Scan Results — Per-run result arrays. Separated for lazy loading.
History — Last 10 scan summaries for the history page.
Current Run — ID of the active scan (for progress display).
PSU Secrets

Encrypted credentials

Client secrets, certificate thumbprints, certificate passwords, managed identity client IDs, AWS access keys, and secret keys. Never stored in the cache — only in PSU's encrypted secrets store, accessed via the Secrets PSDrive.

Serialization Constraint

PowerShell class instances stored in PSU cache serialize to just their type name, losing all property data. The module converts all objects to plain key-value objects before caching. This is a known PSU/PowerShell interop constraint that the module handles transparently.
